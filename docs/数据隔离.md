# 本地开发数据 与 线上生产数据 的隔离方案

> 目标：**两套数据永远互不干扰**——本机测试怎么折腾都影响不到线上，线上同事的录入也不会被本地覆盖。
> 自检命令：`bash scripts/check-isolation.sh`（只读，一条命令给出全部结论）

## 一、两份数据分别在哪里

| | 本地开发 | 线上生产 |
| --- | --- | --- |
| 位置 | 本机仓库 `server/data/sales-analytics.db` | 腾讯云 `/opt/sales-analytics/server/data/sales-analytics.db` |
| 实例标识 | `local`（页面显示「本地开发」） | `production`（页面显示「线上生产」） |
| 访问入口 | http://localhost:5178 | http://1.15.91.150/sales/ |
| 使用人 | 只有你自己 | 同事日常正式使用 |
| 备份 | 无（无需备份） | 每天 02:30 自动加密备份 + 同步 COS |

两份库靠**实例标识（instanceName / instanceId）**区分，实例 ID 在数据库首次启动时随机生成并永久保存。

## 二、三层防护

### 1. 文件层：数据文件不会自己跑
- `server/data/` 已在 `.gitignore` 中，**git 永远不会带走数据库**。
- 部署脚本 `scripts/deploy-cvm.sh` 只打包 `server/src`、`client/dist`、`scripts/*.sh`、`package.json`、`tsconfig.json`；
  打包后会**校验包内不含任何 `.db` / `.env` / `data` 目录，发现即中止**；解包时再一次排除 `server/data` 与 `server/.env`。
- 本地 `server/.env` 不再上传（线上有自己的 `/opt/sales-analytics/server/.env`），本地配置不会覆盖线上配置。

### 2. 应用层：认错了库就拒绝启动
- 启动时比对「数据库内登记的实例」与「本进程声明的实例」（`SA_INSTANCE`，未设置时按路径自动判定：
  `/opt/sales-analytics/` 下算 `production`，其它算 `local`）。
- 不一致 → **打印原因并拒绝启动**（防止把本地库当线上库对外服务，或反之）。
- 任何页面顶部与左下角都有实例徽标：绿色「线上生产」/ 橙色「本地开发」；鼠标悬停显示实例 ID。
- 「设置 → 系统信息」可以看到：实例标识、识别方式、数据库文件与大小、各表数据量、备份份数与最近备份时间。
- 运维监控：`GET /api/health`（无需登录，只返回是否健康与实例名，不含任何路径与业务数据）。

### 3. 运维层：部署 / 备份 / 恢复三处都核对
- **部署**：解包前记录线上指纹（实例、实例ID、inode、各表行数、sha256），解包后再次比对，
  **数据只要有一点变化就中止部署**（不重启、不影响线上）；全部通过后才重启并做健康检查（必须返回 `instance: production`）。
- **备份**：备份文件名带实例名（`sales-analytics-production-20260915-023012.db.gz.enc`），
  日志里同时记录实例 ID 与 sha256；执行前若发现「数据库实例 ≠ 当前环境期望实例」直接拒绝（可用 `--force` 强制）。
- **恢复**：恢复前三道核对——① 备份文件名标注的实例、② 备份内部登记的实例、③ 目标环境的实例，
  任何一处对不上都**默认拒绝**（本地备份恢复到线上会被拦住）；早期没有实例标识的旧备份同样必须显式 `--force`；
  恢复完成后校验 `/api/health` 的实例标识是否与目标一致。

## 三、日常操作手册

### 怎么确认自己现在看的是哪份数据
1. 看页面顶部的徽标：绿色「线上生产」＝同事的正式数据；橙色「本地开发」＝本机测试数据。
2. 或在「设置 → 系统信息」看实例标识与数据库文件路径。
3. 命令行：`bash scripts/db-fingerprint.sh <数据库路径>`。

### 想拿线上数据在本机测试（安全做法）
不要直接改线上库，也不要直接改线上库的副本当作线上用，按下面做副本库：

```bash
# 1) 从线上拉一份快照到本机（只读，不影响线上）
ssh -i ~/Downloads/cbs069791292101.pem ubuntu@1.15.91.150 \
  "python3 -c \"import sqlite3;s=sqlite3.connect('file:/opt/sales-analytics/server/data/sales-analytics.db?mode=ro',uri=True);d=sqlite3.connect('/tmp/copy.db');s.backup(d)\"" \
  && scp -i ~/Downloads/cbs069791292101.pem ubuntu@1.15.91.150:/tmp/copy.db /tmp/prod-copy.db

# 2) 另存为副本库，并把实例标识改成独立名字（关键一步，防止与线上/本地混淆）
mkdir -p server/data/test && cp /tmp/prod-copy.db server/data/test/prod-copy.db
python3 - <<'PY'
import sqlite3
c = sqlite3.connect('server/data/test/prod-copy.db')
c.execute("update settings set v='prod-copy' where k='instanceName'")
c.execute("delete from settings where k='instanceId'")
c.commit()
PY

# 3) 用单独的环境变量启动开发服务（不要写进 server/.env）
DB_PATH=server/data/test/prod-copy.db SA_INSTANCE=prod-copy npm run start -w server
```

副本库的实例名会显示在页面上（`prod-copy`），与线上、本地都不会混淆。

### 线上恢复备份
```bash
ssh -i ~/Downloads/cbs069791292101.pem ubuntu@1.15.91.150
sudo bash /opt/sales-analytics/scripts/restore-db.sh \
  /opt/sales-analytics/server/data/backup/sales-analytics-production-YYYYMMDD-HHMMSS.db.gz.enc
```
（恢复前会自动比对实例；跨环境恢复需显式 `--force`）

## 四、逃生开关（仅限确知自己在做什么时）
- `SA_ALLOW_INSTANCE_MISMATCH=1`：跳过实例一致性守卫（例如临时把线上库挂到本地调试），**用完立刻取消**。
- `scripts/backup-db.sh --force`：实例不匹配也执行备份。
- `scripts/restore-db.sh <文件> --force`：跨实例恢复，或恢复早期没有实例标识的旧备份。

## 五、验收清单
```bash
bash scripts/check-isolation.sh
```
输出全部为 ✓ 即表示：本地与线上实例不同、部署包零数据文件、git 未跟踪数据库、本地配置未指向线上、线上只监听 127.0.0.1。
